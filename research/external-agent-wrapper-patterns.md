# Research: External patterns for agentic coding wrappers/dashboards/terminal orchestration

## Summary
Modern agentic coding products are converging on a **session control-plane** model: one place to launch, monitor, steer, audit, and hand off long-running coding agents. For Pi Agent Board, the highest-impact opportunities are not just more rows in a TUI, but stronger **proof-of-work, permissions, environment/isolation, session search, hooks, and orchestration primitives** around each persisted Pi session.

## Findings

1. **Make the board a real session control plane, not just a process list** — GitHub Copilot’s agents panel tracks sessions across repositories and opens a session view with progress, token usage, session length, logs, steering, stop, archive, and natural-language session history queries. Warp positions Oz as a “single pane of glass” for launching, tracking, auditing, and sharing team agent sessions. Claude Code similarly exposes task lists, transcript viewer, session recap, and PR status in-terminal. [GitHub session management](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/track-copilot-sessions), [Warp Oz](https://www.warp.dev/oz), [Claude interactive mode](https://code.claude.com/docs/en/interactive-mode)
   - **Implication for Pi Agent Board:** add first-class session metadata beyond state/summary: duration, token/cost if available, originator/entrypoint, archive vs delete, PR/branch badge, and indexed transcript/session search.

2. **Attach proof-of-work artifacts to “done” states** — Cursor Cloud Agents attach screenshots, videos, and logs to PRs so reviewers can validate without checking out the branch. Codex reports diffs plus citations to terminal logs/test outputs, and Copilot commits link back to session logs for auditability. [Cursor background agents](https://cursor.com/help/ai-features/background-agents), [Cursor capabilities](https://cursor.com/docs/cloud-agent/capabilities), [OpenAI Codex launch](https://openai.com/index/introducing-codex/), [GitHub session logs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/track-copilot-sessions)
   - **Implication:** introduce a “Review evidence” pane per row: changed files/diffstat, commands/tests run, latest failing/passing output, screenshots/log links where available, and a “Ready for review” grouping distinct from merely `Done`.

3. **Surface autonomy and permission profiles at launch and per row** — Codex separates sandbox mode from approval policy, defaults to workspace-write with network off, and exposes read-only/auto/full-access patterns. Claude Code has permission modes, `/plan`, `/permissions`, and lifecycle hooks that can allow/deny/ask/defer tool calls. Warp Agent Profiles configure autonomy, model, tool access, command permissions, and MCP access. [Codex approvals/security](https://developers.openai.com/codex/agent-approvals-security), [Claude commands](https://code.claude.com/docs/en/commands.md), [Claude hooks](https://code.claude.com/docs/en/hooks.md), [Warp profiles/permissions](https://docs.warp.dev/agent-platform/capabilities/agent-profiles-permissions/)
   - **Implication:** make launch presets visible: `read-only`, `plan`, `edit in cwd`, `worktree isolated`, `full trust`. Persist the selected profile in row metadata and use it to drive warnings, confirmation dialogs, and future Pi permission flags.

4. **Support plan-first steering and mid-run intervention without full attach** — Codex lets users watch plans before changes and approve/reject steps; GitHub Copilot supports follow-up steering prompts while an agent is running; Claude Code has `/plan`, `/batch`, `/background`, `/tasks`, and inline background-session workflows; Warp emphasizes approving/adjusting commands during multi-step workflows. [Codex CLI features](https://developers.openai.com/codex/cli/features), [GitHub Copilot on GitHub](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-on-github), [Claude commands](https://code.claude.com/docs/en/commands.md), [Warp Agent Mode](https://www.warp.dev/ai)
   - **Implication:** evolve peek/reply into a steering surface: show current plan/current tool/current blocker, allow queued follow-ups, add `plan_pending` / `needs_approval` row states, and keep stop/interrupt explicit.

5. **Treat environment readiness and isolation as product UX** — Cursor says environment setup is the most important step for cloud-agent effectiveness, with snapshots, update commands, secrets, multi-repo environments, warnings, and shared tmux terminals. Codex cloud runs tasks through container checkout, setup/maintenance scripts, network policy, `AGENTS.md`, validation, diff, and follow-up. [Cursor environment setup](https://cursor.com/docs/cloud-agent/setup), [Codex cloud environments](https://developers.openai.com/codex/cloud/environments)
   - **Implication:** add per-project preflight cards: cwd trust, clean git status, same-repo concurrency/worktree warning, dependency/test command hints, env-health warning, and remembered launch defaults. This is especially high-impact because Agent Board already runs parallel Pi sessions that can touch the same repo.

6. **Use persistent attach/resume semantics borrowed from tmux and modern CLIs** — tmux’s core value is persistent sessions that can detach, continue in the background, and reattach; control mode exposes pane output and async notifications over a parseable protocol. Codex stores transcripts locally and supports `resume`, including non-interactive resumed runs and remote TUI mode. Warp Full Terminal Use lets the agent read live terminal state, write to the PTY, and hand control back. [tmux man page](https://man7.org/linux/man-pages/man1/tmux.1.html), [tmux control mode](https://github.com/tmux/tmux/wiki/Control-Mode), [Codex CLI features](https://developers.openai.com/codex/cli/features), [Warp Full Terminal Use](https://docs.warp.dev/agent-platform/capabilities/full-terminal-use/)
   - **Implication:** keep rows anchored to stable session IDs, preserve transcripts independently of worker liveness, make attach/detach reversible, and design the event store like a control protocol with stable output, status, and backpressure semantics.

7. **Expose hooks, notifications, and automation entrypoints** — Claude Code’s hook lifecycle covers session start/end, prompt submit, tool use, permissions, notifications, task creation/completion, and stop events. Cursor and Copilot start agents from Slack/GitHub/Linear/issues/PRs/CI events, while Codex exposes OTel events for conversations, tool decisions, and tool results. Warp emphasizes API/SDK-first triggers and returning artifacts/raw conversations. [Claude hooks](https://code.claude.com/docs/en/hooks.md), [Cursor background agents](https://cursor.com/help/ai-features/background-agents), [GitHub Copilot starts](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/start-copilot-sessions), [Codex approvals/security](https://developers.openai.com/codex/agent-approvals-security), [Warp multi-harness orchestration](https://www.warp.dev/blog/multi-harness-cloud-agent-orchestration)
   - **Implication:** formalize Agent Board’s JSONL/status schema as a supported integration surface, then add local hooks/webhooks for `needs_input`, `done`, `failed`, `stopped`, and external “start session” triggers.

8. **Plan for parent/child and multi-attempt orchestration, but keep humans in the supervisor loop** — Warp Oz now runs Claude Code, Codex, and Warp Agent as multiple harnesses in one control plane and supports parallel subagents. Claude `/batch` decomposes large tasks into 5–30 worktree-isolated units. Codex supports explicit subagents and cloud `--attempts` for best-of-N runs, while OpenAI recommends assigning well-scoped tasks to multiple agents simultaneously. [Warp multi-harness orchestration](https://www.warp.dev/blog/multi-harness-cloud-agent-orchestration), [Claude commands](https://code.claude.com/docs/en/commands.md), [Codex CLI features](https://developers.openai.com/codex/cli/features), [OpenAI Codex launch](https://openai.com/index/introducing-codex/)
   - **Implication:** add optional hierarchy/grouping: parent task → child sessions, multi-attempt comparison, per-child model/profile labels, and a merge/review gate. Do not auto-fanout by default; make orchestration explicit and inspectable.

## Gaps
- Some Warp docs pages were rate-limited during fetch; Warp findings rely on fetched official Warp marketing/blog pages plus search-result snippets from official docs. Verify exact docs before implementing detailed Warp-specific behavior.
- Product docs rarely provide comparative success metrics, latency, or retention details. Prioritize with local dogfooding telemetry: which board actions reduce attach frequency, unblock time, and failed sessions.
- This brief focuses on external product patterns, not Pi API feasibility. Next step: map each pattern to Pi extension/session/TUI capabilities and identify which require Pi core changes.
